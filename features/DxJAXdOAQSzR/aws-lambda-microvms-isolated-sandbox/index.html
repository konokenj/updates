新機能の背景

近年、マルチテナントアプリケーションの新たなカテゴリが急増しています。AIコーディングアシスタント、インタラクティブなコーディング環境、データ分析プラットフォーム、脆弱性スキャンツール、ユーザー提供スクリプトを実行するゲームサーバーなど、いずれも「アプリケーション開発者が書いていないコード（エンドユーザーやAIが生成したコード）」を、テナントごとに完全に分離した環境で安全に動かす必要があります。

しかし従来の選択肢は、次の三択のいずれかを強いるものでした：

選択肢 分離性 起動速度 状態保持 問題点
仮想マシン（VM） ✅ 強固 ❌ 数分かかる ✅ あり 起動が遅く、管理が複雑
コンテナ ⚠️ カーネル共有 ✅ 秒単位 ⚠️ 限定的 信頼できないコードを安全に動かすには大規模なカスタムハードニングが必要
FaaS（Lambda Functions 等） ✅ あり ✅ 高速 ❌ なし イベント駆動・リクエスト/レスポンス型に最適化されており、長時間のインタラクティブセッションや状態保持には不向き

この「分離性・起動速度・状態保持を同時に満たすことができない」という課題を解決するために、Lambda MicroVMs が登場しました。

新機能の概要

AWS Lambda MicroVMs は、AWS Lambda の新しいサーバーレスコンピュートプリミティブです。仮想化インフラの管理なしに、分離性・起動速度・状態保持の三要素をトレードオフなく提供します。

コア機能

1. VM レベルの分離

Firecracker 仮想化技術を基盤とし、各 MicroVM は専用のカーネルと専用リソースを持ちます。あるユーザーの実行環境から他のユーザーの環境やホストシステムにアクセスすることはできません。この Firecracker は毎月 15 兆回以上の Lambda Function 実行を支えており、実績あるセキュリティと信頼性を受け継いでいます。

2. 超高速起動・再開（スナップショットベース）

「イメージ作成→起動」モデルを採用しています。Dockerfile とコードから MicroVM Image を作成すると、Lambda がアプリケーションを完全に初期化したうえで、そのメモリ・ディスク状態を Firecracker スナップショットとして保存します。その後の起動・再開はすべてこのスナップショットから行われるため、コールドスタートなしでほぼ瞬時に立ち上がります。

3. ステートフルな実行（サスペンド・再開）

実行中の MicroVM はメモリ・ディスク・プロセス状態をセッション全体にわたって保持します。アイドル時には最大 8 時間サスペンド（一時停止）でき、再開時にはインストール済みパッケージ、ロード済みモデル、作業中のファイルセットがそのまま復元されます。サスペンド中はコンピュート課金が発生しません。

料金体系の概要

Lambda MicroVMs の料金は、Lambda Functions とは異なる仕組みです：

  • コンピュート: MicroVM 稼働中はベースライン分を秒単位で課金。ピーク時の超過リソース（ベースラインを超えた分）は実際に消費した期間のみ課金
  • スナップショット: 読み取り（起動・再開時）・書き込み（サスペンド時）操作ごと、およびイメージストレージ（GB/月）で課金
  • データ転送: 標準 AWS レート

コスト最適化のポイント: アイドル時のサスペンドを活用することで、待機コストを大幅に削減できます。サスペンド中はコンピュート課金が停止し、スナップショットストレージのみの課金となります。

使い方

Lambda MicroVMs の利用は「イメージ作成 → 起動 → 接続・利用 → サスペンド/再開 → 終了」の流れで進めます。AWS Lambda コンソール、AWS CLI、AWS CloudFormation、AWS CDK、または Agent Toolkit for AWS から操作できます。

Step 1: MicroVM イメージの作成

アプリコード（例: app.py）と Dockerfile を ZIP アーカイブにまとめ、Amazon S3 にアップロードします。AWS 提供のベースイメージ（例: public.ecr.aws/lambda/microvms:al2023-minimal）を FROM に指定した Dockerfile を用意してください。

Dockerfile の例（Flask アプリ）

FROM public.ecr.aws/lambda/microvms:al2023-minimal
RUN dnf install -y python3 python3-pip && dnf clean all

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
EXPOSE 5000

CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]

CLI でイメージを作成する

aws lambda-microvms create-microvm-image \
  --code-artifact uri=s3://<bucket>/<path>/artifact.zip \
  --name <イメージ名> \
  --base-image-arn arn:aws:lambda:us-east-1:aws:microvm-image:al2023-1 \
  --build-role-arn <IAM ロール ARN>

Lambda がコンテナビルドを実行し、アプリを初期化したうえで Firecracker スナップショットを作成します。ビルドログは Amazon CloudWatch（/aws/lambda/microvms/<image-name>）にリアルタイムで出力されます。完成したイメージには ARN とバージョン番号が付与されます。

Step 2: MicroVM の起動

イメージ ARN、実行ロール、アイドルポリシーを指定して MicroVM を起動します。

aws lambda-microvms run-microvm \
  --image-identifier arn:aws:lambda:<region>:<account-id>:microvm-image:<イメージ名> \
  --execution-role-arn arn:aws:iam::<account-id>:role/MicroVMExecutionRole \
  --idle-policy '{
    "maxIdleDurationSeconds": 900,
    "suspendedDurationSeconds": 300,
    "autoResumeEnabled": true
  }'
  • Lambda は MicroVM に一意の ID と専用 HTTPS エンドポイント URL を自動で割り当てます
  • ロードバランサーや追加のネットワーク設定は不要です
  • アプリはスナップショットから再開されるため、起動完了時点ですでに動作しています
  • autoResumeEnabled: true を設定すると、次のリクエスト到来時に自動で再開します

Step 3: トラフィックの送信・接続

CLI で短期認証トークンを生成し、X-aws-proxy-auth ヘッダーに付与して HTTPS リクエストを送信します。HTTP/2、gRPC、WebSocket も同じエンドポイント経由で利用できます。

# 認証トークンの生成
aws lambda-microvms generate-auth-token --microvm-id <MicroVM ID>

# エンドポイントへのリクエスト
curl -H "X-aws-proxy-auth: <token>" https://<endpoint-url>/

Step 4: サスペンド・再開

アイドル状態になった MicroVM はメモリ・ディスク状態を保持したままサスペンドされ、コンピュート課金が停止します。

操作 方法
自動サスペンド run-microvm 時に idlePolicy を設定（アイドル時間超過で自動サスペンド）
手動サスペンド aws lambda-microvms suspend-microvm --microvm-id <ID>
自動再開 autoResumeEnabled: true を設定（次のリクエスト到来時に自動再開）
手動再開 aws lambda-microvms resume-microvm --microvm-id <ID>

Step 5: 終了（リソース解放）

セッション終了後は MicroVM をターミネートしてすべてのリソースを解放します。

aws lambda-microvms terminate-microvm --microvm-id <MicroVM ID>

注意点

Lambda MicroVMs を利用する際は、以下の点に注意してください。

1. スナップショット互換性（初期化フックの統合が必要になる場合がある）

MicroVM はあらかじめ初期化されたスナップショットから起動します。そのため、アプリケーション初期化フェーズで一意なコンテンツの生成（乱数シードなど）、ネットワーク接続の確立、エフェメラルデータのロードを行う場合は、サービス提供のフックと統合してスナップショット再開後に再実行する仕組みが必要になることがあります。

2. アーキテクチャは現時点で ARM64（Graviton）のみ

x86 アーキテクチャは現時点でサポートされていません。x86 専用の依存関係やバイナリを使用している場合は、ARM64 対応版への移行が必要です。

3. 最大実行時間は 8 時間

1 つの MicroVM の最大ライフタイムは 8 時間です。8 時間を超えるワークロードには対応していません。長時間のバッチ処理などは設計時に考慮が必要です。

4. 提供リージョンが限定的（現時点）

2026年6月時点では 5 リージョン（バージニア北部、オハイオ、オレゴン、アイルランド、東京）のみの提供です。これら以外のリージョンでの利用はまだできません。

5. Lambda Functions とは別の API サーフェス・別の料金体系

Lambda MicroVMs は Lambda Functions とは異なる API（lambda-microvms サブコマンド）を持ちます。既存の Lambda Functions コードや SDK の呼び出しをそのまま転用することはできません。また、料金体系も全く異なります：

  • Lambda Functions: リクエスト数＋実行時間（GB-秒）で課金
  • Lambda MicroVMs: インスタンス稼働秒単位で課金（MicroVM が起動中はベースライン分が常に発生）

イベント駆動・リクエスト/レスポンス型のワークロードには引き続き Lambda Functions が適しています。両者は競合ではなく補完関係にあります。

6. アイドルコストの管理が重要

MicroVM が起動中（サスペンドされていない状態）の間は、実際のリクエストがなくてもベースラインのコンピュート課金が発生します。コスト最適化のために、アイドルポリシーの適切な設定（maxIdleDurationSeconds の調整）を必ず行い、不要な MicroVM はすみやかにサスペンドまたはターミネートしてください。

7. MicroVM イメージのストレージに最低 1 週間の保持期間

MicroVM Image のストレージには 1 週間の最低保持期間があり、それ未満での削除はできません。短命なイメージを大量に作成するユースケースでは保持コストを考慮する必要があります。
